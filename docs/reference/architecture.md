# Sharpr Architecture Reference

Sharpr is a GTK4 + Libadwaita image organizer written in Rust. It builds its UI in code (no Blueprint), keeps settings in GSettings, persists data in two SQLite databases, runs heavy work on background threads, and needs no network access.

The October 2026 browsing and copy modules are committed in the Phase 0 checkpoint. Unfinished experimental wiring is preserved separately; it is not compiled into the default application.

## Threading

- GTK objects and `AppState` live only on the main thread. Never put GTK objects behind `Arc` or `Mutex`.
- Heavy work runs on `std::thread::spawn` or `rayon::spawn` and sends results back over `async_channel`. Results are drained in `glib::MainContext::spawn_local`. There is no async runtime; do not add Tokio.
- Every result that can go stale is checked against a generation counter before it is applied. This applies to the viewer, thumbnails, virtual views, search, the viewer's bucket summary, and Compare.
- The viewer never hands GTK a very large image to upload on the main thread. An sRGB image with 8-bit channels and more than about 1.15 times the screen in each direction is shown as a screen-sized copy, made on a worker (about 30–70 ms in release for 33–270 megapixels). Zoom math uses the original size, and full resolution loads only when zooming needs more pixels than the copy has.
- **Clipboard image copies** decode on one lazy worker using the oriented export decoder and its 3 GB budget. At most one request waits behind the running decode; newer requests retire older results. GTK only publishes the completed RGBA texture, checks current scope, and shows decode failures. Closing the filmstrip retires its clipboard worker.
- **Visual search** runs EmbeddingGemma 2 in `llama-server` children that listen only on 127.0.0.1 with a random key (D24). They die with the thread that started them (`PR_SET_PDEATHSIG`). Every child runs with `--offline`, and inherited llama.cpp settings (`LLAMA_*`, `HF_*`, `MTMD_*`) are stripped, so an environment that names a remote model can't make it download or replace the installed one.
  - **Indexing:** a `visual-index` thread at nice 19 and idle I/O, requested after every completed fingerprint pass. It embeds each fingerprint without a vector or recorded failure, one image at a time, and writes each vector at once, so passes resume. Its server, with the projector, runs only while a pass has work.
  - **On the graphics card by default:** with a GPU (Vulkan) build in the model folder's `runtime-gpu/` and the `visual-search-gpu` setting on, indexing runs on the first card that `--list-devices` reports with at least 2 GB free. That is about 17 times faster than the processor, with matching vectors. With no such card, or if the GPU server fails to start or dies mid-pass, the pass continues on the processor (2 threads). Queries always use the processor build.
  - **Progress:** the service reports a pace (images per second and time left, once 5 seconds of a pass have run) and when the last pass finished. Library Overview shows indexing coverage and activity, refreshed once a second while open; the header indexing ring is retired (D33). "Rebuild Index…" in the Library Overview asks the service to delete the vector file between passes, never during one.
  - **Queries:** a `visual-search` thread owns a text-only server (identical query vectors, faster start). It starts at the first search and stops after 5 minutes without one. The browse worker blocks on it for the query vector, then ranks the candidates left after scope, disabled folders, and chips. The first page holds the file-name matches and the strong visual matches (`STRONG_RESULT`), up to 200, in the chosen sort order; "Show More" adds weaker matches below them, 200 at a time, closest first (user, October 19, 2026). With no strong visual match the closest 200 show closest first, so a search never comes back empty.
  - **Match strength:** the fifth-best score after subtracting each image's closeness to generic prompts, calibrated on the judged Phase 3 sample. It isn't judged below 50 indexed candidates. The order itself stays plain closeness.
  - **Without a model,** or before anything is indexed, words match file names as before, and the status line says so.
- Content fingerprints are computed by one `fingerprints` thread at nice 19 and idle I/O priority, after launch and after folder opens. Passes over the same library are at least 30 s apart, except one asked for because something under the roots changed (`library_scope_changed`, which the root watch's pass calls), which starts at once; a pass is cancelled when the library or its disabled folders change. Hashed pages are dropped from the page cache. The table `file_fingerprints` caches results by path, size, and mtime; it is rebuildable.
- Folder open runs scanning and reconciliation on a worker. The GTK side fills the store in chunks of 100 rows and yields to the main loop between chunks.
- Search and browse use a single coalescing worker that keeps only the newest job, with a 150 ms entry delay and a cancellable library walk.

- File actions (trash and its Undo, Move to Folder, Rename, Copy to Folder, Duplicate, and Find Copies' trash) run on one `file-jobs` thread (`file_jobs.rs`, GTK side in `ui/window/file_jobs_controller.rs`), one job at a time in the order asked, so an Undo never overtakes its trash. Files in a queued or running job are pending, and repeating an action on them does nothing. Each file finishes or fails on its own; cancel (a toast for jobs of more than one file) stops between files. The view drops files only once the worker confirms them, and the selection moves on only if the image in view was among them. The files a job makes (a copy, a duplicate, a rename, a move into the open folder) are added to the open folder's rows when the job finishes: their size, time and header dimensions are read on a worker, then `LibraryManager::insert_new_files` puts each where a reload in the current sort order would list it (every listing, search result and added row sorts by one rule, `model::library::compare_rows`: the order's key, then the name ignoring case, then the full path), if that folder's load (`is_current_load`) still owns the view and has finished filling it. Nothing else changes: no reload, the selection stays on its image (the filmstrip's `with_quiet_selection` keeps the viewer from reloading it), and the thumbnail generation and scheduler state are untouched. While a search or chips narrow the view, the files go into the kept folder view and show when it is cleared. Closing the window lets the current file finish and skips the rest. Undo finds a trashed file in the home trash and the trash of its drive (`file_ops::trashes_for`); in the Flatpak the trash portal puts files in the host's trash, so the home trash there is `$HOST_XDG_DATA_HOME/Trash` or `~/.local/share/Trash`, not the sandbox data folder.

- **Changes under the roots** (`ui/window/root_watch.rs`): one `gio::FileMonitor` (with `WATCH_MOVES`) watches each library root and each folder the sidebar lists, never a disabled folder, and only on a local drive (asked of GIO on a worker, once per root); roots on a network are left to the focus look. Events for image names, and for folders that appear, ask for one pass after 1.5 s of quiet (at most 10 s after the first event); hidden names are ignored, as the folder scan skips them. The pass has three parts. The sidebar walks the roots on a worker (`SidebarPane::rescan_folders`) and updates its list once, adding rows in place so the selection and scroll position stay; a scan that is already running goes round again instead. `library_scope_changed` asks the fingerprint and visual-index services, which already coalesce and space their passes. Images that appeared in the open folder are listed on a worker and added like a file job's results (`insert_new_files`), so there is no reload and the thumbnail generation is untouched. The same pass runs 200 ms after the window gets the focus back (not more often than every 3 s) and 300 ms after a Move or Copy to Folder finishes, because a destination made in the chooser is not watched yet. Gaps: a folder removed outside Sharpr whose name has a dot, and files put into a folder made a moment ago, are noticed at the next focus look.

Bucket and search results replace the filmstrip's rows in one `splice`, so the sorted model and list view update once per view, not once per row. Creating the row objects stays on the GTK thread: about 11 ms for 6,000 rows in a debug build.

The per-row tag lookup, bucket membership query, and virtual-view path scans moved off the GTK thread on October 12 (Phase 2 item 11).

## Filmstrip And Thumbnail Invariants

The filmstrip is Sharpr's most performance-sensitive surface. Keep these rules:

1. Bump the thumbnail generation whenever the list's contents change (folder, bucket, search, or sort).
2. Every path added to `pending_paths` must be removed on every exit path, including failure and stale drops.
3. The GTK side never blocks on a worker channel, and workers never block on their own bounded queue. Workers send no follow-up requests to their own queue (perceptual hashing was removed October 18, 2026, Work Order item 15), and stale requests are skipped with `drain_stale`; reuse it.
4. Factory bind callbacks do no database or filesystem I/O.
5. Large store mutations are chunked.
6. A result is applied only after both its generation and its path lookup still match. This holds for failures as well as successes: every `ThumbnailWorkerResponse` carries the generation it was requested under, the worker sends no failure from a retired generation, and the GTK side drops any response whose generation is no longer current.
   A folder load likewise holds a token (`LibraryManager::load_token`, new with every `reset_for_folder`, `load_virtual` and `restore_view`) and appends only while `is_current_load` still matches, so two loads of the same folder cannot both fill the store.
7. Visible requests take priority over preload. Extend the scheduler; do not rewrite it.

The thumbnail caches are an unbounded per-view memory cache, a global memory cache (500 entries by default), and a disk cache under `~/.cache/sharpr/` keyed by path hash, size, and mtime. Virtual sort/filter reloads carry the active textures for retained paths into the new rows, even when they have left the global cache; excluded paths leave the active cache.

## Persistence

| Store | Location | Contents | Rebuildable? |
| --- | --- | --- | --- |
| `library-index.sqlite` | `~/.local/share/sharpr/` | folders, images (oriented dimensions, quality; the `phash` columns are legacy, no longer written), bucket definitions (`collections`, including colour and icon), member lists (`bucket_members`), fingerprint caches, and legacy `pipelines`, `pipeline_steps`, and `collection_items` | Bucket definitions and member lists: **no**, they are user data. Image/folder metadata and fingerprints: yes. Preserve all legacy tables and rows. |
| `tags.sqlite3` | `~/.local/share/sharpr/` | `file_tags(path, tag)` and `image_quality` (sharpness) | Tags: **no** |
| GSettings `io.github.hebbihebb.Sharpr` | dconf | libraries, disabled folders, and preferences | No |
| `~/.config/sharpr/settings.json` | config dir | legacy file; current code does not read it | n/a |
| `visual-search.sqlite` | `~/.local/share/sharpr/` | visual-search vectors and failures, keyed by fingerprint and a model key (model and projector hashes plus `PREPARATION_VERSION`), and cached model-file hashes | Yes: delete it to reindex; nothing else depends on it |
| Model folder | `~/.local/share/sharpr-models/embeddinggemma-2/` | the two GGUF files and, for native builds, `runtime/llama-server` with its libraries. Installed by the user (D23); Sharpr only reads it | Yes, by reinstalling |
| Thumbnails and logs | `~/.cache/sharpr/` | disk thumbnails, bench logs, and `logs/llama-server-{images,queries}.log` | Yes |

Rules:

- **Buckets store their own members** (`bucket_members`, since Phase 4). Each row holds a bucket, a file's last known path, and its content fingerprint once known.
  - **Who is a member:** the file at that path, or any file whose cached fingerprint matches and whose size and mtime are unchanged. Identical copies are all members.
  - **Missing members (D42):** a member found nowhere is missing. After a fingerprint pass that read every file, `buckets::drop_missing` runs after `relink` and removes members that are missing, have no copy in the library, and whose root is present (non-empty); the index is backed up to `backups/before-drop-missing-<time>/` (member count checked) first, and one toast names the buckets. Hidden members (outside the roots, in disabled folders), members on an unavailable root, and members whose file is in a trash (`file_ops::trashed_originals`) stay. Until a pass drops them, missing members are counted (Library Overview) but no toast appears on open.
  - **Inheritance is computed at display time:** a bucket shows its own members plus its sub-buckets'. Hidden members in disabled folders don't count as missing.
  - **Edits:**
    - Adding to a sub-bucket doesn't touch the parent's list.
    - Removing removes from the bucket and its sub-buckets, by path and by fingerprint.
    - Rename and reparent change no members.
    - Deleting a bucket deletes its rows (`ON DELETE CASCADE`).
  - **Re-linking:** after every fingerprint pass, `buckets::relink` updates stored members from cached fingerprints within that pass’s root and enabled folders. Excluded stored members remain untouched, and excluded candidates are filtered before any filesystem probe. The viewer’s identical-copy count uses the same scope.
    - Matching is by content, never by name. A member whose file is gone moves to the one unchanged file with its fingerprint. With several identical copies its stored path stays (the bucket shows every copy anyway); with none it stays, as missing.
    - A member whose file is at its path gets that file's current fingerprint: the first one known, or a new one after an edit. If the old content still exists elsewhere, another file took the name: the member follows its content to a single copy, or stays as it is with several.
    - A pass that would move 10 or more members first backs up `library-index.sqlite` to `~/.local/share/sharpr/backups/before-relink-<time>/` and checks the copy's member count; if that fails, nothing changes.
    - Members are fingerprinted first in each pass. The sidebar counts and badge colours then refresh, and an open bucket re-reads its members on a worker and reloads (keeping the selection and search) only if its images changed. So a member moved outside Sharpr shows in its open bucket a moment after the root watch notices the move.
  - **Tags no longer decide membership.** Until the one-time migration, buckets were tag-backed: a member carried every effective tag. Those rows stay in the tag database, untouched.
  - **Migration:** `ui/window/bucket_startup.rs` launches `buckets::migrate` on a worker after window construction, until it succeeds. A preparing state keeps the GTK loop responsive; folder opens, indexing and bucket edits wait for completion. Failed upgrades keep bucket controls disabled and show a persistent error while folder browsing remains available. It backs up both databases to `~/.local/share/sharpr/backups/before-bucket-membership-<time>/` and verifies the backup. It writes each bucket's stored effective-tag members, missing ones included, as that bucket's own members. In the same transaction it checks every bucket's count, marks `schema_meta.bucket_membership_migrated_at`, and stamps `user_version` 2. On failure nothing is written; the app reports it, and bucket edits are refused.
- **Tags are keyed by path string.** Renames and moves made inside Sharpr use `LibraryIndex::relocate_file`: an immediate index transaction carries every bucket path and its cached fingerprint, then performs a no-replace filesystem move and the legacy tag update. SQL failures before moving leave files alone; failed tag updates restore the old filename and roll back bucket changes. Commit failures attempt to restore both file and tags; any failed restoration is reported. Changes made outside Sharpr leave orphaned rows, which are kept. `rename_path` never overwrites them: Rename refuses a name whose missing file still has tags or bucket membership, and Move picks the next free name.
- **Schema versions** live in `PRAGMA user_version` (`src/db_version.rs`): 2 for the library index once bucket membership is migrated (1 before), 1 for the tag database. Older builds refuse a version-2 index; rolling back means restoring the pre-migration backup. Before any setup, a database is opened read-only, and refused untouched if its version is newer than the build supports. Schema changes stay additive. Bump the version for any change an older build must not write to, and add a migration that runs only when the stored version is lower. `schema_meta.schema_version` is legacy, written but never read.
- **Legacy tables and settings keys** (`pipelines`, `pipeline_steps`, `collection_items`, and removed-feature GSettings keys) are never dropped. The code that used them was deleted on October 12, 2026; the tables and keys remain.
  - No code reads them at runtime. The startup step that turned unconverted `collection_items` buckets into tags (`migrate_legacy_collections_to_tags`) was retired on October 18, 2026 (Work Order item 14): it took no backup, and once bucket membership is migrated (version 2) tags no longer decide membership. An old database still opens, and its unconverted rows stay as they are.
- **Reads never delete.** Tag rows for missing or trashed files are kept and hidden: `paths_for_tag()`, `all_tags()`, and `paths_for_all_tags_checked()` filter missing paths, and `stored_paths_for_all_tags_checked()` includes them. The tags come back if the file does.
- **Bucket reads and edits go through `src/buckets.rs`** (GTK-free). They touch only the library index, so the two-database crash window for buckets is gone.

## Output Files

- Crop copies and batch WebP exports decode the source in its displayed orientation (a 3 GB decode budget) and write to a new file. Crop Copy retains the source format (D37) using the existing image/libjxl encoders; PNG/TIFF sample depth and alpha are retained, WebP/JPEG XL crops are lossless, and JPEG is re-encoded at quality 100. Unsupported source formats fail explicitly. Batch export writes only WebP, lossless by default or lossy at a chosen quality, optionally fitted within a size that only shrinks. Batch export runs at the lowest priority and checks for cancellation between images and before keeping each output. The output name is reserved with `create_new`, the data is written to a hidden partial file, and the partial is renamed into place. Encoder flushes are checked, and failed outputs are removed.
- Originals are only ever opened for reading. The exceptions are explicit trash, move, and rename actions. Rename and Move to… go through `file_ops::rename_no_replace`, which never replaces an existing file.
- Duplicate and Copy to Folder stream bytes into the same exclusive `Pending` output mechanism, preserve source permissions and choose `name (copy)` suffixes on collisions. Destination symlinks count as occupied; failed copies remove only their own partial.
- Embedded metadata is never written.

## Packaging And Identity

- The app ID is `io.github.hebbihebb.Sharpr`. The desktop file and metainfo are in `sharpr/data/`.
- The Flatpak manifest (`sharpr/packaging/io.github.hebbihebb.Sharpr.yml`, GNOME 50) builds from `.flatpak-source`, exported by `packaging/sync-flatpak-source.sh` using `git archive` of the committed `sharpr/` tree at HEAD. The sync refuses a dirty tracked tree and records the source commit in `.flatpak-source/COMMIT`. It has no ONNX or Real-ESRGAN modules.
- `Cargo.toml` is the one version source. `app.rs` reads `CARGO_PKG_VERSION`; the metainfo regression checks that it matches, and bundle names use that version. `build.rs` compiles schemas and resources.

## Single-root scope

`ui/window/library_root.rs` changes, adds and forgets roots of the active library (D41); Preferences lists each root on its own row with a switch that disables or enables it as the sidebar's "Disable Folder" does (`SidebarPane::change_folder_ignored`), "Choose…" on the first and "Remove" while another remains; `LibraryConfig::roots()` (`config/settings.rs`) is the one list of roots, the first being the stored `root` and the rest `extra_roots`, which is left out of the stored record while empty. Every library-wide path takes that list: `buckets::visible`, the fingerprint and visual-index jobs, search's whole-library walk, copy counts and Library Overview. Roots may not overlap. Changing the first root keeps it in place; the library id, inactive JSON configurations, legacy folder modes and outside-root exclusions are preserved. Runtime folder trees recurse and have a generation independent of the filmstrip. Every walk of a root (the sidebar scan and `collect_library_image_paths_cancellable`, which feeds fingerprints, the visual index, search and Library Overview) follows one rule from `model/walk.rs`: stay on the root's own filesystem, so network shares mounted under a root such as Home are not crawled, and skip hidden folders; the starting folder is never filtered. The sidebar scan runs on a worker and hands over the folders it finds every 200 ms, so rows are inserted in place as it goes and the first folder opens when it ends. Root changes retire browse results, invalidate thumbnail requests and request new fingerprint/visual-index scopes. Existing fingerprint/vector rows and bucket memberships remain stored, so widening reuses them. Bucket resolution filters candidates before file probes: outside-root and disabled members are hidden, not reported missing.
