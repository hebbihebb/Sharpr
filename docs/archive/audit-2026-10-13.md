# Independent audit, October 13, 2026

Archived evidence, not instructions. One review pass of `08979d0..eda86d7` on
`viewer-reset`; the deployed code is `66f3d94`. The later commits change only
documentation. No remediation was performed.

## Summary

The work materially improves data safety and removes several expensive GTK-thread
operations, but the Phase 1 safety promise is not yet met. Two verified code paths
can discard retained tags or overwrite another image; these should block final
data-safety acceptance, though browsing-only acceptance tests can proceed.
Bucket-opening/search ordering and several presentation defects also remain.
The Phase 3 tools need corrections before their output can justify a go decision.
All ordinary tests passed, but graphical and full supply-chain verification were
unavailable in this sandbox.

## Findings, ranked

**1. P0 — Rename destroys retained destination tags.**
`sharpr/src/tags/db.rs:406`; callers `ui/window.rs:3111` and `:3214`.
Tag B's image, move B away outside Sharpr, then rename A to B's vacant filename.
`rename_path` unconditionally deletes B's retained rows, including bucket tags,
without backup or consent to discard them. The passing
`rename_path_replaces_stale_rows_of_a_vanished_file` test explicitly enshrines this
loss. Missing-file retention therefore does not survive name reuse.
**Confidence: high, code and existing test. Disposition: Phase 1**, refuse or
explicitly preserve conflicting records before moving the file; Phase 4 identity
can resolve the ambiguity later.

**2. P0 — The no-replace fallback can overwrite.**
`sharpr/src/file_ops.rs:90–94`.
When hard-link creation fails, including on FAT/FUSE, the fallback checks the
destination and then uses ordinary replacing `rename`. Another process creating
the destination between those operations loses its file. The Move retry loop
cannot detect this because replacing rename succeeds. Existing tests cover the
hard-link path, not this interleaving.
**Confidence: high in the code reasoning; race not executed. Disposition:
Phase 1**, use an atomic no-replace operation or fail safely when unavailable.

**3. P1 — Search can capture the previous folder as the new bucket.**
`sharpr/src/ui/window.rs:1768,1812,1828`;
`ui/window/search_controller.rs:393`.
Open a slow bucket from folder F and start searching before membership arrives.
Scope changes immediately, but F's store remains. Search captures F under the
bucket scope; bucket completion neither clears that snapshot nor invalidates the
search generation. Either result can overwrite the other, and clearing search
can restore F's images labelled as the bucket. The GTK test waits for bucket
completion before searching, so misses this sequence.
**Confidence: high, traced ordering; no graphical reproduction. Disposition:
Phase 2**, synchronize pending opens with search snapshots and result generations.

**4. P2 — The Info chip reports false bucket membership.**
`sharpr/src/ui/viewer.rs:1383–1392`.
Names are selected by any local tag, across all libraries, rather than every
effective tag in the active library. Add an image to Art › Diffusion, then remove
it from Art: the removal correctly leaves `diffusion`, but the chip still claims
Diffusion membership although that bucket is empty. Extra tags alone also produce
false positives. This pre-existing summary logic now supplies D18's always-visible
membership claim.
**Confidence: high. Disposition: Phase 2**, use the same membership predicate as
bucket opening and add a nested-bucket regression test.

**5. P2 — GTK-thread work remains in the claimed completed paths.**
`sharpr/src/ui/filmstrip.rs:849`; `model/library.rs:518–531`.
Before the first colour map arrives, factory binding still calls `tags_for_path`,
taking the SQLite mutex on GTK. Concurrent cleanup/tag work can hold that mutex.
Bucket/search results also append every row synchronously in `load_virtual`; its
name does not make the store mutation asynchronous. The architecture acknowledges
the latter, but Phase 2 item 11 specified chunking and is marked done.
**Confidence: high in blocking paths; stall duration unmeasured. Disposition:
Phase 2**, remove bind I/O and finish chunked virtual loading before performance
acceptance.

**6. P2 — Updated badge colours do not reach bound rows.**
`sharpr/src/ui/filmstrip.rs:1461,842`.
Add a currently visible image to a coloured bucket, or edit its tag with Ctrl+T.
The worker replaces `path_colors` but does not update existing label classes or
rebind rows. Those classes are assigned only during factory bind; `queue_draw`
does not recompute them. Scrolling away and back can reveal the correct colour.
**Confidence: high, callback trace. Disposition: Phase 2**, refresh bound rows when
the new map arrives; test a visible-row membership change.

**7. P2 — Thumbnail failures lack generation protection.**
`sharpr/src/thumbnails/worker.rs:35,202`;
`ui/window.rs:3468`.
A decode failure always sends a path-only response, and GTK marks any current row
with that path failed. An old request failing after a generation change can poison
a newer view of a repaired/replaced file and suppress scheduling. Success responses
also omit generations, so queued responses cannot satisfy architecture invariant
6. This is an existing gap, not introduced by the deadlock fix; stale-request tests
do not exercise completion after decoding begins.
**Confidence: high in missing guards, medium in reproduction timing. Disposition:
Backlog**, preserve generation through completion and add that regression case.

**8. P2 — Judging-sheet escaping changes identities.**
`tools/benchmark-judge.py:94,124`.
HTML escaping is applied to JSON inside a raw-text script element. Its
`textContent` retains entities: synthetic `blue & green` and `/synthetic/a&b.png`
become `blue &amp; green` and `/synthetic/a&amp;b.png`. Saved judgments then fail to
match report queries/paths, changing relevance scores.
**Confidence: high, synthetic reproduction executed. Disposition: Phase 3**, escape
for script-safe JSON without altering parsed strings; add a round-trip test.

**9. P2 — Judging previews can show the wrong file version.**
`tools/benchmark-judge.py:47–51`.
GNOME thumbnails are accepted without source-freshness validation; generated
previews are keyed only by path. Replace an image at the same path and regenerate
the sheet: its old preview is reused, so the judge scores different pixels from a
fresh model run. Benchmark encoder caches gained size/mtime keys, but this new
judging cache did not.
**Confidence: high, cache-key reasoning. Disposition: Phase 3**, validate source
size/mtime and cached-thumbnail freshness before relevance judging.

**10. P2 — The scorer can falsely pass incomplete evaluations.**
`tools/benchmark-score.py:26–42`.
It evaluates only supplied result rows/categories, without the required 30-query
set or four-category coverage. Synthetic empty results return `gate=True`; one
judged subject query also passes. Missing queries are absent from the denominator,
rather than failing as the rubric requires.
**Confidence: high, both reproductions executed. Disposition: Phase 3**, validate
against the expected query/category set and reject incomplete reports.

**11. P2 — Cleanup's manual-tag promise exceeds its predicate.**
`sharpr/src/ui/window/tag_controller.rs:311`;
`tags/db.rs:351`.
The confirmation says self-added tags are kept, but an unprotected manually added
`4k` or a `png` tag on a PNG is indistinguishable from an automatic assignment and
will be removed. D17 approves the name-based whitelist exception; it does not make
the dialog's provenance claim true. The cleanup test verifies names, not origin.
**Confidence: high. Disposition: Phase 2/D17**, accurately describe the whitelist
before confirmation; do not claim proof that every manual row survives.

**12. P3 — Legacy-migration documentation is incorrect.**
`docs/reference/architecture.md:75` says legacy tables are inert and never migrated
at runtime. `sharpr/src/ui/state.rs:66` still calls
`library_index/mod.rs:1040`, reading `collection_items`, adding tags, and marking
collections migrated, without an automatic backup/count verification.
**Confidence: high; existing runtime behavior. Disposition: Backlog**, correct the
documentation and separately guard that legacy migration before supporting old
databases as a verified upgrade path.

## What checked out

Missing-file reads and trash retain tag rows. Primary-tag removal preserves parent
and sibling membership; rename/reparent include missing members and transactions
roll back failed tag batches. Newer-schema refusal occurs before writable setup,
with byte-preservation tests; legacy table deletion was not introduced. Thumbnail
follow-up sends are nonblocking, and queue stress tests pass. Search candidates are
cached per session and cancelled walks are not cached. D20 removes UI without
dropping tag data; Ctrl+B and keyboard context-menu wiring exist. Copy encoders
retain exclusive output reservation and original-byte regression coverage.

Cleanup uses a protected bucket-tag whitelist, `VACUUM INTO` before deletion, and
one deletion transaction. Its test verifies a readable backup and retained rows;
the UI does not verify backup counts or post-cleanup bucket counts. The accepted
two-database crash window remains outside Phase 1 scope.
