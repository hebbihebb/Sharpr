## Confirmed bugs

### P1 — Renaming a parent bucket orphans all descendant buckets

The rename worker in `sharpr/src/ui/collection_dialogs.rs:303` only replaces
the primary tag on paths holding the renamed bucket's own effective tags. A
child bucket's membership requires every ancestor tag per
`sharpr/src/library_index/mod.rs:991` (`collection_effective_tags` lineage).
Scenario: rename `Trips` to `Travel`; child images still carry `trips`, the
child's effective set now demands `travel`, so the child bucket shows empty
while its images keep a stray manual tag. Reparenting handles this correctly
by walking the subtree in `sharpr/src/ui/window/tag_controller.rs:123`;
rename must do the same.

Suggested fix: snapshot every subtree member path and old effective set before
the rename, replace the old primary with the new primary across the union of
those paths in one checked tags transaction, and keep the existing
compensating rename rollback on failure. Add a regression with a parent plus
child bucket where the child retains its members after the parent rename.

### P1 — Escape after a sort change restores the stale order

`sharpr/src/ui/window/search_controller.rs:91` correctly requests a background
re-sort when the sort changed during search, but the Escape handler in
`sharpr/src/ui/window.rs:2444` calls `restore_browse_view()` and then
`clear_inline_search(true)`, and `sharpr/src/ui/window.rs:3509` bumps both
generations, cancelling that just-spawned re-sort worker at
`sharpr/src/ui/window/search_controller.rs:201`. Scenario: search, switch to
Name descending, press Escape; the filmstrip shows the snapshot's old order
while `state.sort_order` says Name descending, and they stay inconsistent
until the next folder load. The GTK test at
`sharpr/src/ui/window/gtk_tests.rs:137` only exercises the type-to-clear path,
which does not cancel.

Suggested fix: reorder the Escape path so the generation bump happens before
the restore-triggered re-sort, or have `restore_browse_view` apply the pending
sort itself instead of spawning a cancellable worker. Add an Escape-path GTK
case mirroring the existing sort-change case.

### P2 — Partial-file collision aborts a copy instead of trying the next name

In `sharpr/src/export/mod.rs:232`, if the hidden partial path already exists,
the copy deletes its reserved output and fails outright. A stale partial from
a crashed run with a reused PID, or any user file matching that pattern, makes
every copy of that image at that size fail in that session instead of falling
through to the next suffix the way `sharpr/src/export/mod.rs:319` already does
for outputs. Suggested fix: loop the reservation so a partial collision
advances to the next output candidate. The existing test at
`sharpr/src/export/mod.rs:494` correctly proves a pre-existing partial is never
overwritten; extend it to assert the copy succeeds under a different output
name.

## Risks and design gaps

### P2 — Search spawns uncancellable work per keystroke

`sharpr/src/ui/window.rs:2438` removed the old 120 ms debounce and calls the
worker directly on every `search_changed`; each call spawns a fresh thread at
`sharpr/src/ui/window/search_controller.rs:158`. Cancellation is only checked
inside the per-file loop at `sharpr/src/ui/window/search_controller.rs:201`;
the whole-library traversal in `sharpr/src/model/library.rs:758` has no
cancellation token at all (the known open concern), and dimension or aspect
work re-reads every candidate's header via
`sharpr/src/ui/window/search_controller.rs:211` with no reuse of the library
metadata cache. On a large library, fast typing stacks up full traversals that
compete with the current query and with browsing.

Suggested fix: restore a short debounce or single-flight guard, thread the
generation token into `collect_library_image_paths` and its recursive walk,
and consult cached dimensions before falling back to header reads. The
stale-result guard itself is sound: generation, scope, and entry-text checks
at `sharpr/src/ui/window/search_controller.rs:247` correctly drop superseded
results, and successive queries correctly reuse the original candidate set.

### P2 — Two-database crash inconsistency remains (known)

Bucket create, rename, and reparent each commit the library index and the
tags database separately with compensating rollback, for example
`sharpr/src/ui/window/tag_controller.rs:35` and
`sharpr/src/ui/collection_dialogs.rs:312`. A crash or kill between the two
commits leaves an orphan empty bucket, a renamed bucket whose members still
hold the old tag, or a reparented hierarchy with stale ancestor tags, with no
startup reconciliation. Collection import has the same shape and now also
aborts midway on the first failed assignment at
`sharpr/src/collection_export.rs:139`, leaving earlier assignments committed.

Suggested fix if this is to be closed rather than accepted: a startup
consistency pass that recomputes bucket membership from effective tags, or a
written decision accepting the window. Rollback error handling and checked
reads are otherwise correctly surfaced as toasts, and the tags transactions in
`sharpr/src/tags/db.rs:414` genuinely roll back on failure, as the new
trigger-based tests prove.

### P2 — Benchmark methodology cannot yet support a gate decision

A reporting gap, not a claim that any run is wrong. In
`tools/benchmark-image-search.py:89`, a query counts as a hit when any single
expected path appears in the top 20, weaker than the roadmap's "useful top-20
for 80% of queries". The native report at
`tools/benchmark-native-image-search.py:98` records no model or projector
filename, quantization, llama.cpp revision, or thread environment, while the
reference report records dtype but no model revision or library versions, so
quantization and runtime effects are confounded and runs are not reproducible
from the artifacts. Preprocessing differs by construction: both scripts
downscale to 768 px with PIL before model-specific processing
(`tools/benchmark-image-search.py:62`,
`tools/benchmark-native-image-search.py:75`), the native query prompt is a
hardcoded string at `tools/benchmark-native-image-search.py:90` assumed rather
than verified to match the reference `SearchQuery` prompt, and the
prepared-image caches are keyed by path string rather than file content, so a
replaced source silently reuses a stale thumbnail. Latency is one timed sample
per query after one warmup (`tools/benchmark-image-search.py:80`), giving a
noisy p95, and no parity tooling in `tools/` compares native and reference
vectors despite both scripts saving them.

Suggested fix: record model/projector hashes and quantization, runtime and
library versions, and preprocessing parameters in every report; add a parity
script computing per-image cosine agreement and top-20 overlap; keep relevance
as a separate human judgment artifact rather than deriving it from the
expected-any-hit metric.

### P3 — Smaller issues

- Toggling "Whole library" with an empty query does nothing because
  `whole_library` is excluded from `has_filters` at
  `sharpr/src/ui/window/search_controller.rs:22`; it only takes effect once
  text is typed.
- Tag-browser activation at `sharpr/src/ui/window.rs:2513` silently inherits
  prior dimension, quality, and whole-library options plus the previous
  snapshot scope.
- `refresh_tag_summary` still queries SQLite and lists all collections
  synchronously on the GTK thread at `sharpr/src/ui/viewer.rs:1425`, as do the
  untouched create-empty, delete, and color collection flows, even though tag
  chips moved off-thread.
- Crop Copy's save button only enables after the glycin preview loads at
  `sharpr/src/ui/crop_dialog.rs:317`, so formats glycin cannot preview can
  never be cropped even though the export decoder handles them; the overlay
  math at `sharpr/src/ui/crop_dialog.rs:61` assumes the glycin texture
  orientation already matches displayed dimensions, which no test asserts for
  EXIF-rotated sources (exported pixels themselves are proven correct).
- Aspect sorting re-reads every file header twice per folder open through
  `sharpr/src/library_index/mod.rs:138` with no caching.
- `sharpr/src/tags/indexer.rs:7` is orphaned dead code since
  `sharpr/src/tags/mod.rs:1` no longer declares it; deleting the file would
  prevent accidental resurrection of automatic format/resolution tags.
  Making `insert_auto_tags` test-only in `sharpr/src/tags/db.rs:82` correctly
  stops new automatic tags in production.

## What checked out

- Disabled-folder handling is consistent in the new code: scoped candidates,
  restores, whole-library collection, and tag-controller writes all filter
  through the current disabled set; the test at
  `sharpr/src/model/library.rs:1006` proves disabled subtrees are excluded
  from whole-library scans.
- Aspect and resolution logic in `sharpr/src/model/browse.rs:24` is
  orientation-aware, treats the 16:9 ±2% tolerance as relative with the
  boundary included, and sorts unknown dimensions last in both directions.
- Export preserves original bytes, reserves outputs exclusively, checks
  encoder flushes, and rejects oversized WebP before creating the destination.
- Flatpak source checksums match the lockfile exactly for crossbeam-epoch
  0.9.20 and memmap2 0.9.11 (`sharpr/Cargo.lock:386`,
  `sharpr/packaging/cargo-sources.json:499`); a full Flatpak build remains
  unverified, and the yanked chacha20 advisory in the deny log is pre-existing.
